# 第 23 章：跨会话检索与缓存优化 —— 让 Agent 拥有"长期记忆"

## 23.1 问题：会话结束即失忆

大多数 Agent 系统的上下文只存在于单次会话内。会话一结束，之前讨论的方案、踩过的坑、写过的代码，全部丢失。下次遇到类似问题，用户不得不重复描述一遍。

传统的"长期记忆"（Long-Term Memory）只存关键事实，无法按语义检索历史对话的完整上下文。我们需要一个真正的**跨会话全文检索**能力。

## 23.2 解决方案：SQLite + FTS5

### 架构设计

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│ Session A   │────▶│              │────▶│ FTS5 虚拟表  │
│ (对话历史)  │     │ CrossSession │     │ 全文索引     │
├─────────────┤     │ DB           │     │ messages_fts │
│ Session B   │────▶│ (SQLite)     │────▶│              │
│ (对话历史)  │     │              │     │ BM25 排序    │
├─────────────┤     │              │     │ Snippet 高亮 │
│ Session C   │────▶│              │     │              │
└─────────────┘     └──────────────┘     └──────────────┘
                           │
                    ~/.baoclaw/
                    cross_session.db
```

### 数据模型

BaoClaw 的跨会话检索基于 SQLite 的 FTS5（Full-Text Search 5）扩展：

```rust
// 会话元数据
pub struct SessionIndex {

```

### 核心实现

```rust
// cross_session_db.rs

pub struct CrossSessionDb {
    conn: Mutex<Connection>,  // SQLite 连接（同步，用 Mutex 包装）
}

impl CrossSessionDb {
    /// 打开/创建数据库，自动建表
    pub fn new() -> Result<Self> {
        let db_path = home.join(".baoclaw/cross_session.db");
        let conn = Connection::open(&db_path)?;
        
        // 建表
        conn.execute_batch("
            CREATE TABLE IF NOT EXISTS sessions (
                id TEXT PRIMARY KEY,
                cwd TEXT, model TEXT,
                started_at TEXT, ended_at TEXT,
                turn_count INTEGER, cost_usd REAL
            );
            
            CREATE TABLE IF NOT EXISTS messages (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                session_id TEXT REFERENCES sessions(id),
                role TEXT, content TEXT, timestamp TEXT
            );
            
            CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts
                USING fts5(content, content=messages);
        ")?;
        
        Ok(Self { conn: Mutex::new(conn) })
    }
    
    /// FTS5 全文搜索，BM25 排序
    pub fn search(&self, query: &str, limit: usize) -> Vec<SearchResult> {
        let sql = "
            SELECT m.session_id,
                   snippet(messages_fts, '[', ']', '...', 1, 32) as snippet,
                   bm25(messages_fts) as rank,
                   m.timestamp, s.cwd
            FROM messages_fts
            JOIN messages m ON messages_fts.rowid = m.id
            JOIN sessions s ON m.session_id = s.id
            WHERE messages_fts MATCH ?
            ORDER BY rank
            LIMIT ?
        ";
        // ...
    }
}
```

## 23.3 Frozen Snapshot Pattern —— 最大化 Prompt Cache 命中

### 问题

Anthropic 的 Prompt Caching 按前缀匹配：只要前缀相同，就能命中缓存。但如果每 turn 都重建 system prompt 或 tools 列表（哪怕顺序变了），整个缓存就失效了。

### 解决方案

```
Turn 1: [System Prompt | Tools | User Msg 1]
          ↑ frozen       ↑ frozen    ↑ 变化
          ─────────────────────────── 缓存命中 ──→

Turn 2: [System Prompt | Tools | User Msg 1 | Assistant 1 | User Msg 2]
          ↑ frozen       ↑ frozen                                     ↑ 变化
          ─────────────────────────── 缓存命中 ──→

Turn 3: [System Prompt | Tools | User Msg 1 | ... | Dynamic Reminder | User Msg 3]
          ↑ frozen       ↑ frozen                         ↑ 唯一变化点
```

**关键**：System Prompt 和 Tools 列表在会话开始时构建一次，然后**冻结**。每 turn 只有 Dynamic Reminder（动态提醒）变化。

```rust
// query_engine.rs

pub struct QueryLoopConfig {
    // ... 其他字段 ...
    
    /// Frozen snapshot: 只构建一次，永不变化
    pub frozen_system_prompt: Option<Vec<Value>>,
    pub frozen_tools: Option<Vec<Value>>,
    pub frozen_hash: Option<u64>,
}

// run_query_loop 开头：
let frozen_system = build_system_prompt(&config);
let frozen_tools = build_tools_list(&config);  // 按名称排序，确保稳定
let frozen_hash = compute_hash(&frozen_system, &frozen_tools);

// build_api_request 中：
let system = config.frozen_system_prompt.as_ref()
    .cloned()
    .unwrap_or_else(|| build_system_prompt(config));  // fallback
```

### 效果

- **缓存命中率**：从 ~60%（工具顺序不稳定）提升到 ~95%（冻结后前缀完全一致）
- **成本节省**：每个 API 调用的 input tokens 计费减少 90%（缓存部分按 10% 计费）
- **延迟降低**：缓存命中时 API 响应更快

## 23.4 思考

**Q: 为什么用 SQLite 而不是向量数据库？**

A: 对于文本检索，BM25（FTS5 使用的算法）在大多数场景下不逊于向量搜索，且部署零依赖（SQLite 是嵌入式数据库，rusqlite bundled 编译）。向量搜索适合语义模糊匹配（"给我找一个类似 X 的方案"），FTS5 适合关键词精确匹配（"上次 WebSocket 重连怎么做的"）。两者互补，未来可加向量层。

**Q: Frozen Snapshot 的局限性？**

A: 如果系统提示词需要随会话动态变化（如工具健康状态变化导致 tools 列表改变），Frozen 会阻碍更新。解决方案：保持 frozen 的"绝对稳定部分"（系统提示词 + 工具定义），变化部分放在 Dynamic Reminder 中（不参与缓存前缀）。
