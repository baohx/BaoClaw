# 第 25 章：自适应引擎 —— 让 Agent 学会"察言观色"

## 25.1 问题：静态策略无法适应动态场景

Agent 系统中有大量"策略参数"需要动态调整：

- **Compact 的 keep_recent**：保留太多浪费 token，保留太少丢失上下文
- **工具调用**：某个工具连续失败，系统还在傻乎乎地反复调用
- **用户意图**：用户明明在调试，系统却预加载了文档工具
- **上下文窗口**：记忆、Skill、搜索结果争抢有限的 token 预算

这些参数用静态值（硬编码常量）是行不通的。用户在不同场景下需要完全不同的策略。

## 25.2 自适应 Compact

### 核心思想

根据历史压缩效果**自动调整** `keep_recent` 参数：

```
压缩后用户重复问之前的内容？
    → 信息丢失太多 → 增大 keep_recent（保留更多消息）

压缩率很低（只省了 20% tokens）且无信息丢失？
    → 压缩太保守 → 减小 keep_recent（压缩更激进）
```

### 数据结构

```rust
// query_engine.rs

pub struct AdaptiveCompactTracker {
    pub history: Vec<CompactFeedback>,
    pub keep_recent: usize,          // 当前值（动态调整）
    pub avg_compression_ratio: f64,  // 平均压缩率
    pub avg_loss_score: f64,         // 平均信息丢失率
    pub compact_count: u32,
}

pub struct CompactFeedback {
    pub compression_ratio: f64,      // tokens_saved / tokens_before
    pub tokens_before: u64,
    pub tokens_after: u64,
    pub user_repeated_topic: bool,   // 压缩后用户是否重复问
    pub timestamp: String,
}
```

### 调整算法

```rust
impl AdaptiveCompactTracker {
    pub fn record_compact(&mut self, result: &CompactResult, user_repeated: bool) {
        // 1. 记录本次反馈
        self.history.push(CompactFeedback { ... });
        
        // 2. 更新滑动平均
        self.avg_compression_ratio = EMA(history);
        self.avg_loss_score = EMA(history);
        
        // 3. 自适应调整
        if self.avg_loss_score > 0.15 {
            // 信息丢失太多 → 保留更多
            self.keep_recent = (self.keep_recent + 4).min(30);
        } else if self.avg_compression_ratio < 0.3 && self.avg_loss_score < 0.05 {
            // 压缩率差且无丢失 → 压缩更激进
            self.keep_recent = max(self.keep_recent - 2, 6);
        } else if self.avg_loss_score < 0.05 && self.avg_compression_ratio > 0.6 {
            // 理想状态 → 微调
            self.keep_recent = max(self.keep_recent - 1, 8);
        }
        // else: 中等表现，保持当前值
    }
}
```

### 效果

| 场景 | 初始 keep_recent | 几轮后 | 原因 |
|------|-----------------|--------|------|
| 调试（频繁回看之前的错误日志） | 10 | 18-22 | 用户反复问压缩前内容 → loss_score 升高 → 自动增大 |
| 闲聊（不需要历史上下文） | 10 | 6-8 | 压缩率低且无丢失 → 自动减小 |
| 长任务（编写+测试+重构） | 10 | 12-15 | 轻微丢失 → 适度增大 |

## 25.3 工具健康监控

### 三级状态机

```
           连续 3 次失败          连续 6 次失败
Healthy ──────────────→ Degraded ──────────────→ Disabled
   ↑                        │
   └── 连续 5 次成功──────────┘
```

```rust
// tool_health.rs

pub enum ToolStatus {
    Healthy,    // 正常运行
    Degraded,   // 降级：系统提示词中加警告
    Disabled,   // 禁用：暂时从可用工具列表移除
}

pub struct ToolHealthTracker {
    pub records: HashMap<String, ToolHealthRecord>,
    pub degrade_threshold: u32,   // 默认 3
    pub disable_threshold: u32,   // 默认 6
    pub recovery_minutes: u32,    // 默认 30
}
```

### 系统提示词注入

当工具降级时，自动在系统提示词中注入警告：

```
## Tool Health Warnings
⚠️ Tool 'Bash' is degraded (failure rate: 45%, 4 consecutive failures). 
   Consider using an alternative.
```

### 使用示例

```rust
let tracker = ToolHealthTracker::new();

// 记录成功
tracker.record_success("FileRead");

// 记录失败
tracker.record_failure("Bash", "Permission denied");
tracker.record_failure("Bash", "Timeout after 30s");
tracker.record_failure("Bash", "Exit code 1");

// Bash 现在是 Degraded → 系统提示词会加警告

// 检查工具是否可用
if tracker.is_available("Bash") {
    execute_bash(...);
} else {
    // 被禁用，告知用户
}
```

## 25.5 上下文窗口智能分配

### 注意力评分公式

```
attention_score = 0.5 × relevance + 0.3 × recency + 0.2 × frequency
```

| 因素 | 含义 | 来源 |
|------|------|------|
| **relevance** | 与当前查询的相关度 | 意图预测 + 关键词匹配 |
| **recency** | 最近访问的时间衰减 | 指数衰减（半衰期 30 分钟） |
| **frequency** | 被引用的频率 | 历史统计 |

### 分配算法

```
1. 强制包含：System Prompt + Tools（mandatory = true）
2. 计算可选块的注意力评分
3. 过滤低于 min_relevance 的块
4. 按评分降序排列
5. 贪心填充：从高到低，预算够就加，不够就跳过
6. 预算超限 → 裁剪最低分的可选块
```

## 25.6 思考

**Q: 这些自适应机制会不会互相冲突？**

A: 会。例如 ToolHealth 认为 Bash 失败率高要降级，但 IntentPrediction 预测用户要调试（需要 Bash）。解决优先级：ToolHealth > IntentPrediction。工具健康是硬约束（安全/可靠性），意图预测是软提示（辅助）。上下文分配器整合两者：被降级的工具相关度自动降为 0。

**Q: 意图预测的冷启动问题？**

A: BaoClaw 预置了常见模式的种子数据（`observation_count: 10`）。这意味着即使用户从未使用过，系统也能基于关键词做出基本预测。随着真实使用数据的积累，种子数据的影响会被自然稀释。
